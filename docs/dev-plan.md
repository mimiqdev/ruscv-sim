## 1. Objective and inherited profile

Let a host-served device window report a modeled access delay, and charge that delay to the same Platform time that a guest-RAM target's delay already charges, so a slow modeled device costs simulated time without stopping the run, changing a guest-visible result, moving an event or moving the run stop. Today a device transaction is zero-delay by protocol: a host target that annotates any delay is refused. This contract lets the annotation through for a Hart access inside a guest turn, charges it once through the turn's existing delay ledger, and keeps every other device rule. With no host device target, and with a host target that annotates zero, a run is exactly today's run.

The host HTIF contract left the device path zero-delay at these points. `TlmDeviceAdapter::transact` (`src/blocking/device.rs:247-358`) makes one `b_transport` call, validates the response and maps its status; `validate_response` refuses a non-zero `response_delay` (`src/blocking/device.rs:399-408`), a non-zero `host_elapsed` (`:410-419`) and the direct-memory hint (`:421-429`); and `DeviceOutcome` carries only a mapped response and an at-most-one event (`:226-231`), which `SystemBus::finish_device` publishes before returning the response (`src/executor.rs:628-641`). The device trait's own contract says a target "may not let host time pass or annotate delay" (`src/blocking/device.rs:85-96`), and the in-tree targets never call `set_response_delay`, which starts at zero (`src/blocking/in_tree.rs:29-118`, `src/blocking/mod.rs:456`).

The turn's delay ledger belongs to the guest-RAM adapter. `TlmRamAdapter::begin_turn` opens it (`src/blocking/adapter.rs:170-176`), `account_delay` converts a response's delay under the declared tick period, accumulates it into the turn's pending amount and the generation's total, and enforces the declared per-transaction maximum and the turn's conservative bound (`:463-556`), and `take_turn_delay` returns the pending amount once (`:190-198`). `Platform::begin_transport_turn` opens the RAM turn and the bus turn together (`src/machine/platform.rs:371-380`), `Platform::take_transport_turn_delay` reads only the RAM slot's ledger (`:457-459`), and `Machine::step` consumes that amount into the turn's advance before it takes the turn's events (`src/machine/mod.rs:702-707`). The bound itself is `MAX_GUEST_TRANSACTIONS_PER_TURN` = 18 because a straddling fetch is at most twelve transactions and one data or atomic access adds the same six (`src/blocking/mod.rs:357-411`), each reserved at the target's declared per-transaction maximum (`src/blocking/adapter.rs:147-161`); the Platform exposes it from the RAM slot only (`src/machine/platform.rs:468-470`). The C ABI's grant reserves two such turns plus their completion ticks before it starts a step against an inclusive horizon (`src/capi/host.rs:422-437`, `:462-479`).

On the host side the pieces are already in place. The C ABI copies a response's `delay_fs` back for every target, device tables included (`src/capi/target.rs:637`), and `ruscv_target.max_delay_fs` is documented as "the declared per-transaction maximum delay used for every conservative completion bound" (`include/ruscv_sim.h:384-388`); the SystemC initiator sets it to zero unless `--nb` (`integration/systemc/ruscv_initiator.cpp:329-332`). `CDeviceTarget` holds no declared maximum of its own (`src/capi/target.rs:496-510`), and the header tells a device target to leave `delay_fs`, `host_elapsed_fs`, `may_suspend` and `dmi_allowed` zero (`include/ruscv_sim.h:255-270`, `:443-470`). The only thing that stops a C device delay today is the adapter refusal, so the C ABI's response copy already carries the value this contract would charge. Two existing tests assert today's refusal and become this contract's charge tests: `src/machine/tests.rs:2962-2986` (UART) and the `HostHtifFault::Delay(1_000_000)` arm of `src/machine/tests.rs:3673-3723`.

The inherited profile is everything delivered through the completed host HTIF contract: the selectable native or TLM RAM route, `ZeroDelayRam`, declared-maximum delay accounting, direct memory, the quantum with its offset and forced syncs, the non-blocking AT path with its suspension rules, the two device windows with in-tree and host targets, the device events and their single sinks, reset at install, the append-only C ABI and the pinned SystemC 3.0.2 smoke, over the default RV64GC profile with M/S/U, Debug Specification 1.0 and zero-entry PMP plus Sv39.

The inherited Stage 3 performance-certification waiver continues. `tools/a10/public-v1.json`, its fixtures and its pinned argv stay unchanged, and A10 runs only on the native route. This contract makes no wall-clock claim: a device delay is modeled time in Platform ticks, never host time.

Vocabulary used throughout:

- A *device delay* is the non-negative duration a device target reports in `BlockingTransaction::set_response_delay` (`src/blocking/mod.rs:557-559`), or in the C ABI's `ruscv_payload.delay_fs`.
- The *declared maximum* is the route's existing declared per-transaction maximum: `BlockingTarget::declared_max_delay` (`src/blocking/target.rs:47`) on the Rust route, `ruscv_target.max_delay_fs` (`include/ruscv_sim.h:387-388`) on the C ABI.
- The *turn ledger* is the guest-RAM adapter's pending and total delay for one guest turn (`src/blocking/adapter.rs:170-198`, `:463-556`).
- The *turn bound* is that turn's conservative completion bound, 18 transactions at the declared maximum (`src/blocking/mod.rs:357-411`).
- The *grant reserve* is the C ABI's two-turn bound plus one completion tick per turn, which a step must fit before it starts (`src/capi/host.rs:422-437`).
- A *charged device access* is a Hart-initiated device transaction inside an open guest turn, the only class this contract charges.
- A *debug device access* is a `DebugInbound` system-bus access or a Debug Mode Hart-port access, neither of which this contract charges.

Windows and the zero reference | The UART and HTIF windows are the only windows that may annotate, and only a host target has any reason to: the in-tree targets never set the response delay, so an in-tree run charges zero on both routes and keeps today's facts. CLINT, PLIC and the source-1 gateway stay `SystemBus` state and gain nothing. |
| D3. Declaration and bounds | A device delay is declared and bounded by the route's existing per-transaction maximum, not by a new field: `BlockingTarget::declared_max_delay` (`src/blocking/target.rs:47`) for a Rust target and the handle's `ruscv_target.max_delay_fs` (`include/ruscv_sim.h:387-388`) for the C ABI, the value every conservative completion bound already reserves. A delay above it is the existing overshoot host failure (`src/blocking/adapter.rs:528-545`); an unrepresentable delay is the existing conversion host failure (`:478-486`); neither becomes a guest fault. The turn bound keeps its 18-transaction count and its arithmetic: every fetch transaction is RAM, and a turn's data access is either six RAM/walk transactions or five RAM walk transactions and one device transaction, so `17 x maximum + device maximum <= 18 x maximum`. Therefore `Platform::turn_completion_bound_ticks` (`src/machine/platform.rs:468-470`), the quantum's representation check (`:168-190`), `interrupt_latency_bound_ticks`, the C ABI's `bound_ticks`/`wake_bound_ticks` (`src/capi/host.rs:422-437`), `deadline_blocked`, `residual_slack_fs` and `candidate_bound_fs` keep their values for every selection, and a host-device run keeps its in-tree parity run's bound facts. This contract does not add a second declaration, a trait method or a bound extension; the existing bound's coverage extends to the device transaction because that transaction occupies one of the transactions it already reserves. |
| D4. Charging | The charged amount is the device response's own delay, converted and accumulated by the one `TlmRamAdapter::account_delay` implementation (`src/blocking/adapter.rs:463-556`) through one new crate-internal entry on the RAM slot. That entry takes the access's address and the counted flag, uses the same per-access round-up, declared-maximum overshoot, turn-bound check, pending amount, generation total (`transport_delay_femtoseconds`) and guest-turn window as a RAM response, and adds no second accounting path. The rule does not branch on who supplied the target: an in-tree target's delay would be charged by the same entry, and the in-tree targets simply report zero. `SystemBus::finish_device` (`src/executor.rs:628-641`) gains the initiator and charges before it publishes the window's event, so a charge that fails returns the host failure and publishes nothing. A response that maps to a terminal status — `Ok`, a guest-visible fault or `GenericError` — is charged exactly once, as the RAM adapter charges a terminal response (ADR-0004 §5.3); an `Incomplete` response, a validation failure and an unknown completion are charged nothing, because a modeled annotation is untrusted in a response that does not vouch for the access, and the host elapsed time of a runtime failure is a separate fact this contract does not add. `host_elapsed_femtoseconds` stays zero for device transactions. |
| D5. Ordering, events and run stop | The event stays where it is: the window's sink runs inside the access, before the store retires (`src/executor.rs:628-641`, `src/machine/platform.rs:251-277`). The charged delay is modeled time consumed after that access completes: it joins the turn's pending amount and enters the turn's advance before the boundary takes the turn's events (`src/machine/mod.rs:702-707`), so the `PlatformExit` classification still reads the same turn's events at the same turn (`src/executor.rs:2538-2548`), with `mtime` already advanced by the charge. An event is therefore never delayed to its annotated time, an annotation never reorders events, never chooses an exit code and never moves the stop to another turn; a guest observes the delay only as `mtime` and timer progress, and `mcycle`/`minstret` do not change. A faulted or unknown access publishes nothing, as today. The F1 rules are unchanged: a Hart device access flushes the local offset under the bus lock before the target sees it and marks the turn, so the target observes committed time and the turn ends in a sync (`src/executor.rs:987-997`, `src/machine/mod.rs:769-772`); the device charge is part of the same turn's advance that the sync commits. |
| D6. Debug and SBA | A `DebugInbound` device response must still report zero delay, and a non-zero one is a protocol failure of that access, unchanged from today (`src/blocking/device.rs:399-408`). A Debug Mode Hart-port device access carries `Hart` provenance but runs outside an open guest turn, so its delay is validated against the declared maximum and not charged, exactly the guest-RAM adapter's debug rule (`src/blocking/adapter.rs:463-556` charges only while the turn window is open). No device access outside a guest turn moves Platform time, and `ExecutionResult.cycles`, the turn budget and the ISA counters are untouched. |

## 3. Ownership, ordering and events

The Platform keeps the window map, the pre-target policy, routing, the event queue, the single sink, the presented lines and the turn ledger; a device target owns one window's register state and may annotate that window's access time. The Machine converts and consumes the annotation exactly as it converts and consumes a RAM target's. No device target owns `mtime`, `mtimecmp`, an interrupt line or an exit code; the annotation can only make the Machine advance the time it already owns. The Hart is unchanged and never sees a transaction, an event or a delay.

| Window | Base and size | Delay today | This contract |
| --- | --- | --- | --- |
| UART | `0x1000_0000`, `0x100` | Must be zero; in-tree target annotates nothing | A host target may annotate up to the declared maximum; a Hart access in a guest turn is charged; the in-tree target stays zero |
| HTIF | `0x4000_8000`, 8 | Must be zero; in-tree target annotates nothing | The same rule; the Platform's RMW envelope stays target-free and uncharged |
| CLINT | `0x0200_0000`, `0xC000` | `SystemBus` state, no device transaction | Unchanged; no annotation |
| PLIC | `0x0C00_0000`, `0x40_0000` | `SystemBus` state, no device transaction | Unchanged; no annotation |
| Source-1 gateway | `0x4000_0000`, 4 | `SystemBus` state, no device transaction | Unchanged; no annotation |

The next table is the complete rule for D2–D6. "Charged" means the delay enters the turn's pending amount and the generation's transport total through `account_delay`, exactly as a RAM response's delay does; "validated" means the declared-maximum and conversion checks run without a charge. Any other response rule — a changed address, command or length, a second event, a wrong-window event, an event on a read, an event on a non-`Ok` status, a non-zero host elapsed time, a direct-memory hint, or a `DebugInbound` delay — remains a protocol failure of that access, and an unknown completion keeps its precedence and publishes nothing.

| Request | May annotate | Charge | Event | Run stop |
| --- | --- | --- | --- | --- |
| Hart access, in-tree UART or HTIF | No; the target reports zero | None | Unchanged | Unchanged |
| Hart access, host window, no annotation | Yes, zero | None | Unchanged | Unchanged |
| Hart access, host window, annotation `d` | Yes, `d` at most the declared maximum | Once, inside the guest turn; a fault consumes it | Published at the access, before the store retires | The same turn's `PlatformExit` decode, after the charge is committed |
| Hart access, host window, delay above the maximum | Represents a broken target | Validated and accumulated before the overshoot failure, as for RAM (`src/blocking/adapter.rs:528-545`) | None | Host failure, no run result |
| Hart access, host window, a refused response | Irrelevant | None | None | Protocol or unknown-completion failure |
| Debug Mode Hart-port access to a device window | Yes | None; validated only, because no guest turn is open | None | Unchanged debug boundary |
| `DebugInbound` (SBA) access to a device window | No; zero required | None | Same rule as the Hart row | A debug-boundary exit event still stops as today |
| HTIF AMO envelope, UART atomic rejection | Never a target | None | One `HtifWrite` for the envelope, as today | As today |
| Typed tohost dword write, typed UART byte write | No target call | None | One published value or byte, as today | As today |
| CLINT, PLIC or gateway access | No | None | Unchanged | Unchanged |
| Guest-RAM access | nb D4 rules | nb D4 rules | Must be none | Unchanged |
| `receive` and every host view | No transaction | None | None | None |

| `delay-u1-debug-zero` | `DebugInbound` zero-delay rule in `TlmDeviceAdapter::validate_response` | An SBA access to a device window that annotates a delay is a protocol failure and charges nothing | U1 |
| `delay-u2-abi` | C ABI copy of a device response's `delay_fs` | A C device table that annotates one tick adds that tick to the charged delay of its run | U2 |

The retired `device-u2-zero-delay` control's patch removes the same zero-delay check, which is no longer a refusal for a Hart access; its test becomes `a_host_uart_that_annotates_a_delay_charges_it_once`, behind `delay-u1-charge`.

SystemC fault-option controls are not mutation-runner cases, because that runner runs only `cargo test --offline --all-features` and D10 keeps `--all-features` free of a C++ toolchain. U3 owns them as options of the smoke binary in the style of `--fault-uart-wait`. `scripts/test_systemc_smoke.sh` runs each with its own failure assertion, and a run that passes with one set is a smoke failure:

- `--fault-device-delay-above-max`: the selected host device target annotates `max_delay_fs + 1` fs on every completed response. The run must report `result state=failed` with the overshoot diagnostic naming the declared maximum, the access's event must not be published, and the values accepted before it must be exactly the ones the guest wrote.
- `--fault-uart-wait` and `--fault-htif-wait` under a non-zero `--device-delay-fs`: the target waits one tick and reports host elapsed time. The run must still report `result state=failed` with the host-elapsed device-callback diagnostic and publish nothing for that access, which proves that accepting a delay did not accept host time.

Keep the mutation patches, commands and expected assertions under the existing mutation-runner pattern. The standard gate and the no-ledger rule are unchanged.

## 5. Exclusions and retained direction

No device host elapsed time or suspension inside a device callback, no `may_suspend` on a device transaction, no non-blocking device transport or device phase, no device direct memory, no device atomic envelope, no second outstanding device transaction, no device target for CLINT, PLIC or the source-1 gateway, no SystemC-modeled interrupt line or interrupt controller, no second declared maximum, no change to any ABI struct, window code, event tag or error code, no change to the in-tree answers, the RAM target, direct memory, the quantum, the non-blocking AT path or the native and flat routes, no UART inspection snapshot for a host-served window, no fromhost register or host-to-guest input, no HTIF console decoding in the crate, no DMA, multi-Hart, arbitration or coherence, no checkpoint or restore, package or crate publication, A10 change, ACT4 selection change, wall-clock performance claim, or new ISA extension or profile. Issue #207 stays open outside this contract.

Retained direction, each needing its own approved contract: device host-time annotation and suspension inside a device callback, only if it can compose with the quantum or explicitly refuse it; SystemC-modeled interrupt lines; CLINT or PLIC targets only if time and line authority move under an accepted ADR amendment; a UART inspection snapshot for a host-served window; and HTIF fromhost, console input and syscall proxying through a host-served endpoint.

## 6. Activation boundary

This documentation-only rotation archives the host HTIF contract, applies the bounded 2026-11-08 device-delay amendments to ADR-0002 and ADR-0004, and activates this target atomically on merge. It does not assert runtime support, start implementation, change the dev image, publish a release or seal an oracle. Later implementation must meet the units above on its own reviewed commits.
