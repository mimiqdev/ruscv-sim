# Development Plan

**Current milestone on rotation merge:** TLM Direct Memory Interface

**Status:** Current approved target, activated by this contract-rotation merge. Until that merge, `main` retains Blocking TLM and SystemC Transport as Current. On merge this is the sole Current contract and the [entire blocking-transport contract](archive/milestones/blocking-tlm-systemc-transport.md) becomes historical. Activation changes no simulator behavior and makes no implementation-completeness claim.

**Authority:** Normative milestone contract, constrained by accepted ADR-0001–0004 and their amendments through the 2026-11-05 direct-memory amendments to ADR-0002, ADR-0003 and ADR-0004. Source code and behavioral tests establish implemented behavior; CI and PR history retain check and review outcomes.

**Approved:** 2026-11-05. After the blocking transport, the maintaining agent selected direct memory access for qualified guest RAM (the retained next step of post-A7 roadmap Stage 7) as the next milestone under the owner's delegation of full planning authority, and selected decisions D1–D14 below, all recommended choices. The [proposal entry](proposals/post-tlm-dmi.md) is informational, not another current contract.

## 1. Objective and inherited profile

Let a Hart read and write qualified guest RAM of the TLM route through a target-granted host pointer instead of one `b_transport` per access, with no second Hart execution path and no architectural difference. A run with direct memory enabled produces the same architectural, fault, event and time facts as the same run with it disabled, including after invalidation, across reset and after a failure.

The inherited profile is everything delivered through the completed blocking-transport contract: the selectable native or TLM RAM route, the in-tree `ZeroDelayRam`, the atomic extension, declared-maximum delay accounting, the `capi` C ABI and the pinned SystemC 3.0.2 smoke, over `rv64imafdc` by default with M/S/U, Debug Specification 1.0 and zero-entry PMP plus Sv39. The `src/tlm` component vocabulary, including its unused DMI types, stays unchanged and unrouted.

In this contract "direct memory" is the TLM Direct Memory Interface of IEEE 1666. It is unrelated to the RISC-V Debug Module Interface, which the source calls `dmi` in `src/dm`, `src/jtag` and the Machine debug hub. New identifiers use `direct_mem` or `BlockingDirectMem`, not a bare `dmi`, except the user-facing `--dmi` option and field `MachineConfig.dmi`.

The inherited Stage 3 performance-certification waiver continues. `tools/a10/public-v1.json`, its fixtures and its pinned argv stay unchanged, and A10 runs only on the native route. This contract makes no wall-clock claim: its proof that accesses left `b_transport` is transaction counts, not timing.

## 2. Selected decisions

References are unchanged from the archived blocking-transport contract: ISA Manual 20250508, Debug Specification 1.0 at `5695c0aaa7a3c228e14702e1268eb5a5e50e3cb8`, IEEE 1666-2023 (SystemC, including TLM-2.0), and Accellera SystemC 3.0.2 at commit `70b0fc8e4a74acc677b0fc73cea08f940c2115d5`. The OpenOCD, Spike and riscv-arch-test pins are unchanged, and the dev image is unchanged.

Every decision below was approved on 2026-11-05 under the delegation recorded above. Existing comments in `src/blocking`, `src/capi` and `integration/systemc` that cite `dev-plan` D numbers refer to the archived blocking-transport contract; new code cites `direct-memory D<n>` for this contract.

| Decision | Accepted selection |
| --- | --- |
| D1. Delivery | One bounded cut of roadmap Stage 7: direct memory for the guest-RAM target of the blocking TLM route, in Rust first, then the C ABI, then the SystemC smoke. Non-blocking transport, TLM-modeled devices and temporal decoupling are later contracts. |
| D2. Selection | `MachineConfig` gains a public `dmi: bool` field; `MachineConfig::new` selects `false`, and this breaks struct-literal construction. `dmi` with `Transport::Native` is the existing `MachineError::UnsupportedTransport`; the `Flat` rule is unchanged. `run --dmi` exposes it and requires `--transport tlm`; `--dmi` without it is a CLI error. With `dmi` false the adapter issues no direct-memory query, ignores every hint and behaves exactly as the blocking-transport contract. The `RiscVSimulator` and `load_and_run*` facades keep the native route. The CHANGELOG names every public addition: the field, the new `BlockingTarget` methods (each with a default that offers nothing, so existing implementors compile), the new blocking vocabulary and the D12 C ABI additions. No other public signature changes. |
| D3. Grant protocol | IEEE 1666 shape. A target may set a `dmi_allowed` response hint on a completed non-atomic transaction. Only after a hint, and only when the access was Hart-initiated, the adapter queries `get_direct_mem_ptr` once for that address and access direction, before the response returns. A grant carries the inclusive physical start and end, the host pointer of the start byte, the granted access (read, write or read-write), and the read and write latencies in exact femtoseconds per access. A denial caches nothing and is not an error. A grant that does not contain the queried address, or has a null pointer, an inverted or overflowing range, no access, or a latency above the target's declared per-transaction maximum, is a protocol failure of the access that queried it. A panic in the query, or a contained C++ exception, is an unknown completion of that access and poisons the transport. No grant failure is guest-visible. |
| D4. Fast path | The direct path lives only inside `TlmRamAdapter`, below the validated physical access boundary, in the existing RAM slot. No Hart, ISA, MMU, TLB, decoder or DM code sees a host pointer or a grant. A bounded region cache in the adapter holds grants; eviction is invisible except in transaction counts. One Hart-initiated `Fetch`, `DataRead` or `DataWrite` request whose whole span lies inside one cached region with the required permission copies its bytes through that pointer with no `b_transport` call. Anything else takes `b_transport` unchanged: a span crossing a region end, a missing permission, and every `DebugInbound` request. An access is never split or merged, so a straddling access stays one transaction. |
| D5. Permissions | Fetch and data reads need read; stores need write. A store to a read-only region takes `b_transport`, so the target decides its status under the blocking mapping, and a hint on it may produce a read-write grant that replaces the old region. A new grant replaces every cached region it overlaps. PMP and Sv39 checks run above the boundary and are unchanged. |
| D6. Latency and time | One direct access charges the grant's read or write latency exactly as one `b_transport` response annotating that delay: the same conversion, the same accounting by outcome, the same debug-not-charged rule and the same boundary total, through one shared code path. The declared-maximum turn bound is unchanged, because D3 bounds every latency by that maximum and each direct access is one transaction of the worst case. A target whose latency equals the delay its `b_transport` annotates for that access gives identical Platform time with direct memory on or off. `mcycle` and `minstret` never include it. |
| D7. Atomics and reservations | LR, SC, every AMO and Sv39 A/D updates always take the one-transaction atomic `b_transport`, whatever regions are cached, per ADR-0002 §8. A target's SC check reads per-byte committed-write versions that a direct store does not update, so a completed guest LR opens a write-suspension gate in the adapter: while it is open every store takes `b_transport`, so the target records the write and the SC outcome matches native. A conclusively completed guest SC closes the gate, successful or failed; a faulted SC leaves it open, as the Hart retains its reservation. Sv39 A/D updates are themselves LR and SC envelopes that create no Hart reservation, so they carry a page-table-update marker on `AtomicRequest` and neither open nor close the gate; without it a walk inside a guest LR/SC sequence would close the gate on a live reservation. Reset closes it. A gate left open by an LR with no SC is correct and only slower. Reservations stay per-Hart architectural state. A direct store also increments the adapter's committed-write record before returning, under ADR-0002 §6. |
| D8. Invalidation | The adapter registers one `BlockingDirectMemInvalidator` with the target through a new `BlockingTarget` method when a Machine with `dmi` is composed; the invalidator holds the adapter weakly, so a dead Machine's is inert. `invalidate(start, end)` is inclusive, callable at any time from any thread, including synchronously inside `b_transport`, and removes every overlapping region. It takes only a dedicated direct-memory lock that is never held across a target call, and a direct copy holds that lock, so when `invalidate` returns no copy through a removed pointer is in flight and none can start. A grant being installed is discarded if an overlapping invalidation arrived since its query began. Because no pointer is held above the adapter, the next access after an invalidation takes `b_transport`, which is authoritative, and no extra Machine boundary is needed (2026-11-05 ADR-0004 amendment). |
| D9. Reset, failure and lifecycle | Before calling a target's transport reset, the Platform drops every cached region and closes the D7 gate, so no pointer outlives a reset. An unknown completion drops every region at the moment it poisons the transport, and a poisoned transport refuses the direct path as it refuses `b_transport`. Teardown and Platform recomposition drop every region. A late attempt to use a removed pointer therefore cannot change a reinstalled image, and D6 of the archived contract stays true. |
| D10. Target obligations | A grant is an `unsafe` promise, so `BlockingDirectMemGrant::new` is an `unsafe fn` that states them: the pointer stays valid for the whole range until the target has called `invalidate` for it; it addresses the same bytes `b_transport` and `transport_dbg` serve, so a write through any of the three is visible to the others at once; and nothing else accesses those bytes concurrently with the Machine. A target invalidates before it frees, moves, remaps or narrows a granted range. A shared `Arc` target with more than one live Machine registered must revoke every grant and deny new ones while that holds. |
| D11. Architectural interactions | No decoded-instruction or translated-code cache exists, and fetch reads through the same route, so self-modifying code and `FENCE.I` work with no new mechanism; the fixture proves it. Software breakpoints are `ebreak` bytes written by the debugger through SBA or program-buffer stores, and D10 aliasing makes them visible to the next fetch. The profile has no hardware triggers, so no trigger check can be bypassed. A TLB holds translations only, and page-table walks read through the same route. Host views, `tohost` polling and installation stay on debug transport. |
| D12. C ABI | Additive: `ruscv_target` gains a final nullable `get_direct_mem_ptr` callback; `NULL` means no direct memory, and a non-NULL callback selects it, so `ruscv_machine_create` keeps its signature. `ruscv_payload` gains a final `dmi_allowed` response field. A `ruscv_direct_mem` struct carries the query and the D3 grant. `ruscv_machine_invalidate_direct_mem(machine, start, end)` is the D8 entry. It is the one exception to re-entry rejection: it is accepted inside a callback, on the creator thread only, and touches only the shared invalidator, never the handle's run state. Every other ABI call from a callback is still rejected. The D10 obligations bind the C target, and the header states them. |
| D13. In-tree and SystemC targets | `ZeroDelayRam` and the SystemC `RamTarget` set the hint on completed non-atomic transactions and grant one storage chunk as read-write with zero latency. Each invalidates everything before discarding chunks in its transport reset. `ZeroDelayRam` follows the D10 shared-target rule. The SystemC target uses `register_get_direct_mem_ptr`, the initiator uses `register_invalidate_direct_mem_ptr`, and `integration/systemc` gains a `--dmi` option. Time-equivalence controls use a separate test target with non-zero latency. Because the initiator runs a grant on one `SC_THREAD` with no `wait()` inside it, target-side invalidation arrives only between grants or synchronously inside a callback. |
| D14. CI and documentation | The guest suite and the SystemC smoke add a direct-memory pass; no new CI job and no dev-image change. `cargo build`/`test --all-features` still need no C++ toolchain. `docs/integration/systemc-tlm.md` becomes normative for direct-memory grant, permission, latency, invalidation, lifetime and FFI rules; quantum and synchronization stay open there. The README, CLI help, CHANGELOG and verification docs state `--dmi`, the `MachineConfig` change and the C ABI additions. |

## 3. Ownership and semantics

The Machine owns the `dmi` selection as composition configuration; the Platform owns the region lifetime through its RAM slot, as amended in ADR-0003. The direct path is another completion mechanism inside the existing TLM implementation of the validated physical boundary, per ADR-0002 §8, not a second Hart path, and it never substitutes for an atomic operation. The target owns the bytes and the grant; the adapter owns the choice to use one. In the SystemC host the external kernel still owns global time, and latency reaches it only through the consumed amount of a grant.

These are requirements for subsequent implementation. Activating this contract does not implement them.

| U1. Grants and read path | Per D2–D6, D8–D10 and D13 for reads: the vocabulary, `MachineConfig.dmi`, `run --dmi`, hint, query, grant validation, region cache, fetch and load through the pointer, read latency, invalidation and reset, with `ZeroDelayRam` granting read-only for now. | U2. Write path and atomics | Per D4–D7: write and read-write grants, direct stores with write latency and committed-write recording, the D7 gate and the full `ZeroDelayRam` grant. A non-zero-latency test target gives identical Platform time, `mtime` and boundary delay total with `dmi` on and off, and debug-mode latency is not charged. |

SBA reads and writes stay counted transactions, and a host view sees direct stores. Native results and A10 unchanged. |
| U4. | U6. Exit | Per D14, the documentation is complete and accurate. Every §4 negative control is registered. Dependencies: U1 first. U2 requires U1. U3 and U4 require U2 and may proceed in parallel. U5 requires U4. U6 requires all.

Required negative controls, under the existing mutation-runner pattern:

- `MachineConfig::new` selecting direct memory, or a query issued with `dmi` false;
- an LR, SC, AMO or A/D update served through a pointer;
- a direct store while the D7 gate is open, so an SC succeeds that fails on native;
- a D7 gate closed by a faulted SC, or closed by an A/D update's SC;
- an invalidation ignored, or a raced grant installed after it;
- a pointer retained across transport reset, or used after an unknown completion;
- a store through a read-only grant, or a load through a write-only grant;
- a span crossing a region end served by the pointer;
- a `DebugInbound` access served by the pointer;
- a malformed grant accepted, including a latency above the declared maximum;
- direct latency not charged, or charged into `mcycle` or `minstret`;
- a direct store left out of the committed-write record;
- `ruscv_machine_invalidate_direct_mem` accepted on another thread, or a second ABI entry accepted inside a callback.

Keep their small patches, commands and expected assertions under the existing mutation-runner pattern. The standard gate and the no-ledger rule are unchanged.

## 5. Exclusions and retained direction

No `nb_transport`, TLM phases beyond blocking, TLM-modeled CLINT/PLIC/UART/HTIF, direct memory for any device, multiple RAM targets, SystemC-modeled interrupt lines, temporal decoupling or quantum keeper, multi-Hart or DMA, inbound masters other than the existing DM, block execution or translated code, host-pointer caching above the adapter, hardware triggers, grant-time snapshotting, non-Linux FFI targets, package or crate publication, A10 change, ACT4 selection change, wall-clock performance claim, or new ISA extension or profile.

Quantum and temporal-decoupling policy remains open and needs its own contract. Non-blocking transport requires a separately approved timing contract. Stage 8 remains conditional.

## 6. Activation boundary

This documentation-only rotation preserves the entire blocking-transport contract, applies the bounded 2026-11-05 direct-memory amendments to ADR-0002, ADR-0003 and ADR-0004, and activates this target atomically on merge. It does not assert runtime support, start implementation, change the dev image, publish a release or seal an oracle.
